    rpcMessage passes those through and falls back to humanizeError otherwise.
    humanizeError itself is unchanged — no existing call site changes behaviour.

app/carrier/app.js (truck form)

  - LB001 now separates the trailer-VIN message from the insurance-schedule one

    can no longer leave it stuck on "Saving…"
  - the no_coi panel says a truck cannot be added until the COI is verified,
    instead of promising a save the database refuses
  - the success toast used tone 'ok', which is not in TONE — a successful save

8. migrations/bl_fix_0304_carrier_status_jsonb_cast.sql  (new)
   + humanizeError now names the SQLSTATE  (app/shared/errors.js)
--------------------------------------------------------------------------
Carrier directory -> open a carrier -> Approve had never worked. Neither had
"Send back": both call cc_set_carrier_status, which is declared RETURNS jsonb but
assigns the TEXT result of cc_set_carrier_status_core into a jsonb variable. The
bare word 'active' is not valid JSON, so every call died on SQLSTATE 22P02 after
the core had already done its work, and the update rolled back with it.

It stayed hidden because the throw comes from the wrapper (nothing reaches the
audit log as a refusal) and humanizeError had no 22P02 branch, so the only thing
anyone ever saw was "Something went wrong. Please try again."

to_jsonb() fixes it; signature and client are unchanged. Applied to staging then
production and verified on production inside a rolled-back subtransaction:
22P02 before, PROBE_OK returned="active" after.

errors.js: an unrecognised error now appends its SQLSTATE — "(code 22P02)". Five
characters of standard Postgres vocabulary, not SQL text or a stack trace, and it
turns an unreproducible report into a one-line diagnosis.
