The seven changes in that right-hand column. (1) The icon is the real LoadBoot app icon — icon-192.png, the same asset the website, the Play app and every push notification already use — with a tone-coloured ring and a small event glyph on the corner. The brand stays on every row; the glyph is what tells you at a glance whether this is a document, a truck or a payment. (2) All five tones are used. The portal already defines urgent / warning / action / success / info in its global TONE map, and the notification row throws four of them away — it colours only urgent, success and "everything else blue". (3) Repeats collapse: eight Document received receipts become one row with ×8. (4) Relative time — "12 min ago", not "Aug 29, 2026 · 1:38 PM". (5) An explicit action button, pointed at the exact card using the deep links shipped today (#documents/insurance, #fleet/add-truck). (6) Day separators, so a two-month backlog stops reading as one wall. (7) A Needs you filter, because that is the only question a carrier is actually asking.

One rule that would fix the read rate on its own. A nudge about a thing should supersede the last nudge about that thing, never stack beside it. Top Knotch carries six unread general reminders plus four about the same certificate — ten unread notifications describing one missing document. One open nudge per subject, rewritten each time, and the Alerts tab becomes a to-do list instead of a log.

6Where a notification actually lands

Every notification written to app_private.notifications shows up in three places inside the portal, and a fourth outside it. The tap destination is decided by lbNotifDest(), which reads payload.url and falls back to keyword matching on the title — so even a notification saved without a url still opens a sensible tab.

Two real bugs in the push path. (1) push-send always sends a url field, defaulting to "/". The service worker has a sensible default of /app/, but it never applies, because the field is never absent. So a push sent without an explicit destination opens loadboot.com — the marketing homepage — instead of the portal. (2) The service worker supports coalescing (options.tag + renotify) and push-send never sets a tag. So ten reminders about one certificate stack as ten separate notifications in the phone's shade, exactly as they stack in the Alerts tab.

7What is built but has never fired

About 120 template keys exist in the database functions and have never appeared in the notifications table — offer.received, pay.incoming, trip.pickup_late, pod.approved, the whole trip and settlement layer. That is not a bug: no broker has posted a load on production and no settlement has ever run, so the code has simply never been reached.

It does mean the entire load-to-payment notification path is untested in production. The day the first load moves, that path runs for the first time on a real carrier. It is worth firing each one once on staging before that happens, rather than discovering the shape of the payload during someone's first booking.
