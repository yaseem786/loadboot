Agent payout: reviewable "Other" methods, support-signed outreach

Two independent pieces of work: a real review path for alternative agent
payout rails, and the outreach signature change from founder to support desk.

--- Agent payout: "Other" was unreviewable (migrations 0209, 0210) ------------

An agent picking "Other" got a single free-text box and nowhere to put the
receiving-account coordinates. Petar Travica (Croatia, Revolut, W-8BEN) signed
up with account_title only - no bank name, IBAN, SWIFT or addresses - and the
reviewer's only options were to verify blind or reject a legitimate agent.
The amber warning said "do NOT pay" without naming what was missing.

Backend (bl_agent_0209_payout_other_review.sql):
  * cc_agent_payout_request_details(user, fields[], note) - staff-only. Flags
    payout_status='info_requested', stores the requested field list, and sends
    the agent an in-app notification plus a branded email listing exactly what
    is needed. Authenticated-only grant.
  * cc_agent_payout_approve_method(user, note) - staff-only. Records that the
    RAIL can receive an international USD payment in the agent's own name.
    Deliberately separate from cc_agent_payout_verify, which is about the
    account numbers. Refuses outright if IBAN/account or account_title is
    missing - an approved method with no account number is how a payout run
    fails silently weeks later.
  anon-executable SECURITY DEFINER count unchanged at 27.

Two latent bugs surfaced while wiring the agent side, both fixed in
bl_agent_0210_payout_merge_and_echo.sql:
  * agent_save_onboarding REPLACED payout_details wholesale. An agent returning
    to add just an IBAN would have wiped their uploaded ID, bank proof, tax
    data and the reviewer's own flags. Now merges; null/empty incoming keys are
    dropped so a blank box never erases a stored value. Re-submitting after an
    info request clears 'details_requested' and returns payout_status to
    'pending' so the row re-enters the normal queue.
  * agent_onboarding_status stripped payout_details entirely, so the portal
    could neither prefill the form nor show what staff had asked for. Now
    returns the agent's own coordinates to the agent's own session, minus the
    tax TIN (SSN/EIN stays write-only).

Frontend:
  * app/carrier/app.js - "Other" now renders provider name, IBAN/account,
    SWIFT/BIC, provider address and beneficiary address, all required on
    submit. Wizard state is seeded from the saved payout_details (previously
    the nested jsonb never reached the flat payout_* keys, so returning agents
    saw empty boxes). New "Action needed" screen: under_review no longer locks
    an agent out of the very form staff asked them to fix - it lists the
    requested fields and opens the payout step.
  * app/command-center/views/agents.js - payout card shows the bank rows for
    'other', computes and names the missing fields inside the warning, adds
    "Request receiving details" and "Approve this method", turns the warning
    green once the method is approved, and gates "Verify bank details" behind
    that approval. Shows a pending-request line while waiting on the agent.
  * app/shared/api.js - ccAgentPayoutRequestDetails, ccAgentPayoutApproveMethod.

Verified in production: the approve-method guard correctly refuses Petar's
profile (no IBAN); the details request delivered to ptravica90@gmail.com at
23:06 UTC and his payout_status is now info_requested.

--- Outreach signature: founder -> support desk (migration 0208) -------------

Owner decision. All 15 outreach_templates rows now sign as Riley / Carrier .
Broker . Shipper Support rather than Muhammad Yaseen / Founder. "Riley" is the
identity that already answers the phone line and places onboarding calls, so a
reply or callback resolves to a consistent contact instead of an invented
employee. Three in-body lines ("you are talking to the founder, not a sales
team", "not a support queue", "the founder reads this inbox") were rewritten -
leaving them would have contradicted the new signature inside the same email.
The migration ends with a guard that raises if any template still carries
founder/Muhammad. Transactional templates and the email shell are untouched.

Reply-rate should be watched against the founder-signed baseline of the last
10-14 days.

Migrations are applied to production; the JS changes need push + deploy.
